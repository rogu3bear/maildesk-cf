# Source publication qualification

This optional, local-only path separates publication of an exact source commit
from a named historical cache incident. It does not qualify deployment, provider
operations, mail, migration, or cleanup. The historical receipt stays unchanged
and its unknown outcome and retained payload remain protected. The pre-push hook
has no fallback CI or retry: missing, stale, incomplete, untrusted, or changed
qualification records hold the push.

A source qualification is not an archive. Before a new CI run, independently
qualify current writer/output custody, protect all retained incident payloads
and other owners' work, and obtain normal Disk Guard admission for the exact
command and complete write paths. Preserve the original incident receipts. A
current-state archive must not be described as the old failure-time image. The
single compiler-root contract remains in force.

After those prerequisites and a clean committed candidate, the owner may run
`build-and-retire.py` with its existing exact resource request, a fresh proof
directory, an actual authorization reference, `--retain-cache`, and the exact
command `bash scripts/ci.sh`. The retain option only prevents the finalizer from
retiring cache; it does not protect files from build-time replacement. The
qualified run requires normal launch acknowledgement, both stream EOFs, a zero
exit, no unknown process generations, and observed natural reservation release.
An unproved settlement remains held and cannot issue a qualifying lifecycle
record. No enclosing-lifetime marker substitutes for genuine admission.

Native settlement records population coverage, independent known-birth reads,
and exact reservation observations separately. A population or registration
error does not suppress lease polling. Current unknown process scope is recorded
as `live_generations: null`; current unknown lease state is
`exact_reservation_released: null`. Last successful values and their observation
times are retained separately, never presented as fresh liveness or release.
Known-birth entries identify the expected birth and the time and result of that
individual read. Any unresolved observation error remains sticky for the operation, even
if later reads succeed. Exact release, direct exit and stream EOF cannot repair
unknown producer coverage or qualify an old failed operation.
An initially unlocked exact descriptor establishes current release state only.
The natural-release flag requires an observed held-then-released transition on
that same descriptor; it does not require or substitute for launch acknowledgement.

The native population reader still requires full same-UID identity coverage;
it does not exclude an unreadable peer using only session or process-group
membership. The SDK's child-list interfaces describe current relationships,
not a retained birth-bound ancestry history. A relationship-first exclusion
needs a separately qualified complete relationship/identity contract covering
session changes, reparenting and PID reuse; none is enabled here. Unresolved known,
same-session, descendant or unrelated identities therefore retain
the hold. This observer supports bounded synchronous producer chains, not
universal observation of forks between samples.

The primary reader is an in-process, SDK-compiled `kinfo_proc` backend. It reads
the complete bounded `KERN_PROC_ALL` population, projects every current same-UID
identity, and independently reads each known birth with `KERN_PROC_PID`. It does
not fall back to another interface after a denial. All syscall errors, including
`EPERM` and `ENOMEM`, partial or malformed records, duplicates, capacity overflow,
unsupported ABI and a missing observer preserve UNKNOWN. A successful zero-length
PID response requires independent `kill(pid, 0)` `ESRCH` to establish absence;
an existing PID or denied probe stays UNKNOWN. A denied PID response never probes
another interface. Birth tuples
remain kernel start-time seconds and microseconds. A numeric session ID comes
from `getsid`, bracketed by records with matching birth, UID, parent and process
group. Drift refuses the sample. This remains sampled coverage, not an atomic
whole-host history or universal fork observation.
The published kernel iterator omits still-being-forked (`SIDL`) processes and
internal shadow records before exposing runnable entries; this limitation is
explicit, not an exclusion inferred from a denied identity. Registered births
still require independent reads. A surfaced in-creation or malformed record is
UNKNOWN, and a missing record never proves nonexistence without the absence check.

Backend preparation uses separate small normal Disk Guard admissions in a fresh
owned namespace, before the main producer. It never changes retained products.
The retained settlement and launch binding identify the backend source, compiler,
SDK dependency headers, platform, compilation command and actual artifact bytes.
Inputs must remain stable through compilation, and the loaded artifact's identity
must remain unchanged. There is no shared mutable helper cache or environment
override for backend selection. Production proof retains its backend namespace;
disposable tests own and close their temporary namespaces.

Each compiler admission declares its unique backend directory as its output
lane. The enclosing resource request must lease the operation's proof directory
(including Python fixture temporary directories), as well as every product root
including `build`. Full CI places Python fixture temporary files beneath its
fresh proof so nested compilers inherit that coverage. Capacity/write-path
coverage alone does not grant an output lease; missing parent coverage holds.
The growth estimate and inherited reservation descriptors remain unchanged.
The ordinary workflow's pure `operation_resource(repo, output, original)` planner
adds only missing `build` and exact fresh proof lanes already covered by the
caller's write paths. It preserves a fully declared request byte-for-byte and
records the original request's SHA-256 in a derivative's estimate basis. The
effective request and digest are retained in `operation.json`; the seed file is
never edited. A required output outside the original write scope fails before
admission. Manual qualification requests must declare these same exact outputs.

This is a platform-bound macOS build diagnostic. Both libproc and `kern.proc`
records are SDK-declared private/SPI interfaces, with no general future-platform
stability promise. See Apple's [`sysctl(3)` contract](https://developer.apple.com/library/archive/documentation/System/Conceptual/ManPages_iPhoneOS/man3/sysctl.3.html)
and [kernel process-node implementation](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/kern/kern_sysctl.c).
The installed SDK defines the record layout; unsupported layouts and preparation
failures hold before the main producer. This prospective replacement does not
identify the denying policy in historical runs or reclassify any failed receipt.
Complete same-owner zombies retain the existing no-executable-writer meaning
even after their group or parent fields have been cleared. Immutable birth and
owner validation precedes that classification; drift remains UNKNOWN.

The size-checked native ABI also returns bounded diagnostics from the same call:
failure stage, syscall result/errno, reported length and capacity, target PID,
and identity/session fields already read, with explicit known-field flags.
Python retains these in sticky operation errors without further diagnostic
probes. Missing data stays unknown; receipts contain no process names or arguments.

Native ABI v4 exports the installed SDK's `P_WEXIT` bit. Complete matching birth
and owner records with an affirmative exit flag can project an explicit `exiting`
identity, with session/parent/group set to null rather than invented. The backend
retains each generation's raw flags and any session result/errno already observed.
For a record already flagged as exiting, it does not request live-only session
data; an attempted session denial remains fatal. Birth/owner drift and an
exiting-to-active regression remain fatal.

Every same-UID exiting identity is conservatively live, regardless of relationship.
Independent known-birth reads continue until validated zombie or kernel absence;
the flag itself never proves exit. Launch registration and acknowledgement require
complete active identity and no pending exits. `maildesk-native-state/v1` receipts
retain current `pending_exits` and immutable `exit_transition_history`; settlement
requires an empty current pending set. Existing deadlines, sticky failures, stream
EOF and exact reservation release requirements remain unchanged. Publication
validates this state schema and backend source binding for new native-reader runs;
older receipts retain their original source-bound meaning.

The CI child records inputs after frozen Bun installation and before the checks,
then captures them again with products after all checks. Both captures must match
for source, complete environment projection, CI script, dependency-resolution
and selected toolchain bindings. Products cover the five Worker bundle trees,
router WASM, UI Worker and UI site. The retained lifecycle record binds the
operation, settlement and run capture. This is evidence for review, not an
independent approval. `source_qualification.py` requires clean exact HEAD/tree,
locked offline Cargo metadata and external package source trees, the installed
node_modules tree, selected tools, Rust sysroot, SDK, wasm-pack cache and product
trees. Unavailable required files, escaping symlinks, ambiguous tool selections, changing
inventories, or unavailable metadata hold. Confined dangling links are recorded
with their unresolved state; an escaping or changed link remains a hold. A stable writer exclusion must be
established separately; a hash scan by itself cannot establish it.

The environment projection retains every variable value in a digest except the
lifecycle's own validated CI/admission markers and the canonical Cargo target
that CI unconditionally selects. The pre- and post-check CI captures must match that projection exactly. The
push environment has a separate, independently approved digest of the
source-reviewed publication projection; it is not equated to the CI environment. An unreviewed
change to either binding holds. The historical environment digests do not
establish equivalence for a new run. The
selected tool and dependency inventory is an explicit review target, not a
claim that OS version text alone authenticates every system dependency.

Before publication, an independent reviewer must review the exact successor,
run-bound evidence and guard source, and supply a separately expected review
digest. An operator-owned, mode-0600 `var/source-publication/selection.json`
selects one proof directory, the preserved incident receipt, one target ref,
expected remote SHA, remote name and remote URL digest. Separate owner-only
`approval.json` and `review.json` bind the exact capture, lifecycle, source,
incident and review. Three separately installed local Git configuration pins
(`maildesk.sourcePublicationSelectionSha256`,
`maildesk.sourcePublicationApprovalSha256`, and
`maildesk.sourcePublicationReviewSha256`) must match the canonical JSON digests.
The review pin must come from the independent reviewer, not from a self-authored
reviewer-name field. The source owner does not manufacture the review or its
expected digest. Exact schemas and required fields are defined in
`source_qualification.py` and verified by its fixture tests.

The guard rereads the original incident and requires its exact pinned digest and
`CACHE_RETAINED_SETTLEMENT_UNPROVED` status. It verifies the digest-bound capture,
input, lifecycle, operation, exit and settlement records, separately pinned review
and operator approval, current Git HEAD and tree, the separately approved full
push environment, and one non-deletion fast-forward ref update to the pinned
target and remote. Approval `maildesk-source-publication-approval/v2` includes
`publication_environment` as an exact object with `schema` set to
`maildesk-publication-environment/v2` and `sha256` set to the canonical
publication environment projection digest at the hook. Legacy v1 approvals,
unversioned digests, and malformed binding objects hold; they are not upgraded
or interpreted under the new algorithm. Lifecycle
markers are rejected there, not accepted as custody. The source owner and reviewer
must review the guard and the precise operative environment binding; transient
context variables can cause a safe hold. The projection validates the installed
1.0.3 dispatcher contract: exact worker, runner, core, dispatcher binary and configuration digests,
selected interpreter and fixed control values. It strictly parses the bounded
job, binds its kind, exact repository hook path and digest, and push arguments,
and rejects extra fields. Only the result filename is removed after checking
that it names an absent `result.json` in an owner-only, non-symlink
`ops-hooks-` directory under the system temporary root. This output location
is allocated by the installed dispatcher and is not an input to the source
verifier. The result directory and its owner are trusted only for this narrow
classification; neither the job nor its environment establishes dispatch.
All other variables remain bound except shell nesting, previous-directory,
color preference, and `CODEX_TOOL_CALL_ID`. The latter is validated as an
optional, nonempty, at-most-256-byte identifier without control characters and
reported separately as presence plus a SHA-256 hash; its raw value is never
printed or included in approval equality. In three deliberately refused real
Git observations at candidate `f7018e3` (one dry run and two normal-form pushes),
all 71 projected key names matched and only that identifier's value hash changed
between observations. Scoped source searches found no consumer in the reviewed
dispatcher, global hooks, Disk Guard, Maildesk scripts/hooks, or Python crash
reporter. This evidence classifies that one identifier as invocation audit context;
it does not reconstruct the uncaptured environment of the earlier failed push
or establish future stability. The owner-only observation receipt is
`var/source-publication/diagnostic-f7018e/receipt.txt`. The verifier uses `-B`
and invokes Git directly. The repository
hook separately requires the installed global chain's `--verify-chain pre-push`
check, including effective hooks path and registered hook digest. A direct
`.githooks` configuration or missing registration holds. This code does not
change that configuration or register a pin.

Git-source publication consumes Git objects, not the live build outputs or
installed dependencies. The guard therefore does not re-read mutable products,
node_modules or toolchains at push time. Their run-bound digests support review
of that qualification only: they do not prove that live files still match, that
those products were published, deployed, installed, or accepted, or that every
system dependency is covered. Capture during CI still needs qualified custody
for the full observation and protection of retained outputs before that run.
The independent reviewer must assess those limits and accept the exact evidence.
The guard does not edit the records, change the old exit status, assume unknown
processes ended, or send mail. Normal global Git guards and repository hook
content pinning remain required; a modified hook needs independent review and
supported pin registration before it can execute.

After independent hook review and supported registration, an operator can obtain
the projected digest without a push by invoking the installed global pre-push
hook with the exact remote name and URL and **empty stdin**. The global chain
runs its normal pinned delegate; the verifier prints the versioned environment
binding and redacted invocation audit, then rejects empty ref input even if all
records already exist. This inspection does not send refs or authorize
publication. The operator binds the schema and digest into the separate
approval; changes to any operative value hold. The
standalone `--print-publication-environment REMOTE URL` command requires the
same validated dispatcher context and is not a substitute for the global chain.
The actual global-chain route and independent pin must still be qualified after
registration; a disposable dispatcher fixture is narrower evidence.

For a deliberately refused environment diagnostic, an operator may set the
local Git configuration `maildesk.sourcePublicationDiagnostic` to exactly
`true` after reviewing this source and the pinned hook. After the normal chain
and dispatcher validations, the diagnostic emits a bounded report containing
only operative projected key names and SHA-256 value hashes, aggregate digest,
the separate redacted invocation audit, exact
candidate identity, hashes of remote arguments and hook input, and hashes of
the selected controls and configured pins. It always refuses before any approval
can authorize publication. No raw environment values are printed. The local
setting must be removed through normal configuration before a later publication;
invalid or repeated settings hold. A diagnostic observation does not recreate a
previous process environment, create authority, or replace independent review.
